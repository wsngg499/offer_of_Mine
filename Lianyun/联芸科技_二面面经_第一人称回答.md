## 1. 挑一个项目，用 5～6 分钟重点介绍。

**第一人称回答：**

我选工业采集终端项目来介绍，重点讲业务链路、我的职责，以及通信和升级可靠性这两个方面。

**第一，项目要解决什么问题。** 这个终端用于现场温度、压力采集，以及风机和继电器控制。设备需要把运行状态传到云端，也要接收远程命令和更新固件。如果每次调整软件都到现场接线，维护成本会比较高，所以我把本地采集控制、4G 联网和远程升级组织成一套完整流程。

**第二，整体架构怎样划分。** 底层由 GD32 管理采集与输出，通过 4G 模块接入网络，业务层使用 MQTT 与 OneNet 交互。Application 负责正常业务、上报、命令解析、心跳、掉线重连和固件下载；独立 Bootloader 负责镜像检查、安装和启动管理。存储上，内部 Flash 放 Bootloader 和运行应用，外部 W25Q64 暂存固件，EEPROM 保存版本和升级状态。W25Q64 的容量是 64 Mbit，也就是 8 MiB，具体分区地址要结合 MCU 型号和链接配置确定。

**第三，我具体承担什么。** 我主要负责通信与升级软件，包括联网状态管理、MQTT 消息处理，以及独立 Bootloader、串口 IAP 和 OTA 的实现与联调。我介绍职责时，会把自己完成的模块与整个系统区分开，不把所有硬件和全部业务功能都算作个人独立开发。

**第四，通信部分怎样考虑可靠性。** 我会把模块就绪、入网、建立连接、在线和重连这些阶段放进状态机。网络断开时，本地采集和控制应继续运行，上报数据进入有界缓存，恢复后再补传。命令处理除了看消息是否收到，还需要考虑命令是否重复、是否过期、参数是否合法，以及如何返回执行结果。缓存也必须有容量上限和溢出策略，否则长时间断网会变成内存或存储问题。

**第五，升级链路怎样组织。** 我的核心思路是把下载与安装分开。新固件先写入外部 Flash，下载不完整时不擦内部运行应用；收到数据后检查长度、偏移和范围，再写入并验证。完整镜像通过校验后，记录待安装状态并重启，由 Bootloader 擦写内部 Application，回读检查后再启动。Bootloader 跳转时还要检查应用向量表、清理自己使用的中断和外设状态，并设置应用栈指针和复位入口，不能直接调用应用的 main。

**第六，异常恢复怎样区分。** 下载时断网或掉电，重点是确保持久化进度不领先于实际数据；安装时掉电，内部应用可能不完整，Bootloader 应重新检查外部镜像并恢复安装。新版本启动后业务异常是另外一类问题，只有保留有效旧镜像并实现试启动、健康确认和回滚，才能保证回到旧版本。我会根据代码实际完成的功能说明恢复边界，不把“有 Bootloader”直接等同于“有 A/B 回滚”。

**最后，怎样验证。** 我会围绕正常升级、下载中断、错包、重复包、版本不匹配和安装掉电组织测试，观察系统是否误跳转、误提交进度或失去恢复入口。材料中记录单次升级约 4 分钟，解释这个指标时还需要带上固件大小、网络条件和统计起止点。这段项目对我最大的帮助，是让我把驱动、协议和状态恢复联系起来：一次读写成功只是基础，长期运行和异常中断后仍能恢复，才说明链路设计比较完整。

**口述提示：** 按背景约 40 秒、架构与职责约 70 秒、通信约 50 秒、升级约 100 秒、恢复与验证约 80 秒练习，再根据自己的语速调整。本版没有新增“最近完成时间”、具体 MCU 料号或未证实的性能数据。

## 2. 你是怎样实现升级过程中的掉电恢复的？

**第一人称回答：**

我把“断电升级”理解为升级过程中掉电后能够恢复，断电期间本身不能继续执行升级。我的处理分三个阶段。

1. **下载阶段：** 新固件先存在外部 W25Q64，当前内部应用保持可用。必须先写数据、等待完成并回读验证，再保存已确认进度。重新上电后核查检查点；若扇区部分写坏，要按擦除粒度恢复，不能假设原位置可直接覆盖。
2. **安装阶段：** Bootloader 开始覆盖内部 Application 前，要有可靠的安装状态和完整的外部镜像。中途掉电后不跳转残缺应用，而是重新验证镜像并按恢复策略安装；重新安装不要求必须有旧版本，完整的新镜像也能作为恢复来源。
3. **首次启动阶段：** 如果要处理“能启动但业务不正常”，还需要试启动、健康确认和启动失败计数。自动回滚还以保留有效旧镜像为前提，没有实现这些机制时，我只说明支持重新安装或恢复入口。

状态记录本身也可能被掉电打断，所以我会用可校验的双副本或日志式记录，先完成新记录再选为有效状态，并验证每个状态转换附近的断电情况。

**准备备注：** 双副本、断点粒度和自动回滚的实际实现仍需查工程；设计思路不作为未经确认的已实现经历。

## 3. 描述 Bootloader、APP 和 A/B 分区，以及启动、升级、跳转 APP 的全过程。

**第一人称回答：**

我先区分两个概念：内部双应用 A/B，和外部保存新旧两份镜像，并不是同一种布局。现有项目明确的是内部 Bootloader 加 Application、外部 W25Q64 暂存固件、EEPROM 保存状态。

如果采用外部双镜像设计，A、B 可以分别保存已确认镜像和候选镜像，但它们只是存储位置，不等于都能直接执行。安装或回滚仍要由 Bootloader 搬到内部运行区；新版本确认之前，不能破坏唯一有效的旧备份。若采用内部 A/B，则要额外解决两槽的链接地址、启动选择或重映射等问题。

整个流程我按以下顺序解释：

1. **复位进入 Bootloader。** 芯片按启动配置从向量表取得初始栈指针和复位入口，执行启动代码并进入 Bootloader。
2. **判断启动路径。** 初始化必要接口，读取升级状态，判断是否有完整候选镜像、是否处于安装中，以及当前应用是否有效。
3. **执行安装或恢复。** 候选镜像经过型号、长度和完整性检查后，按内部 Flash 约束擦写 Application，再回读验证。失败时保留恢复路径，不标记为可启动。
4. **准备跳转。** 验证应用初始 MSP、Thumb 复位入口和地址范围，停止 Bootloader 的 SysTick、DMA 与外设中断，处理待处理中断，并按芯片能力设置向量表。
5. **进入应用。** 用可靠的底层实现切换栈并跳到应用 Reset_Handler，让应用自己的启动代码初始化。若有试启动机制，再由应用完成自检并提交健康确认。

我的分区说明会以真实链接文件为准，不会把外部双存储直接说成内部双 APP，也不会凭准备材料报具体地址。

## 4. 开发中遇到过哪些比较严重的问题？

**第一人称回答（参考案例，核实后再作为个人经历口述）：**

我会选一个能讲清证据和个人修改的问题。例如升级恢复中，如果持久化进度领先于 Flash 实际写入，重启后可能跳过一段坏数据，这会直接影响固件完整性。

我会先固定掉电发生的位置，对比云端分包序号、EEPROM 记录的偏移和 W25Q64 回读数据。如果确认原因是先提交进度、后完成数据写入，就把流程改为“写数据、等待完成、回读验证、提交进度、对外确认”。恢复时还会检查最近扇区，处理掉电留下的部分编程状态。

复测不能只做一次正常升级。我会在数据写入前后、状态提交前后和应答丢失时分别中断，确认不会跳过坏包，不会因重复包多算进度，也不会在镜像不完整时进入应用。

**准备备注：** 原资料未提供这个案例的真实故障与修复记录。若并未实际发生，面试时应换成自己的真实问题，沿用“现象—证据—根因—个人修改—复测结果”的结构。液压项目 TXE/TC 案例同样需要记录支持。

## 5. 程序跑着跑着跑飞了，怎样排查？举三个故障寄存器，说明具体怎么看。

**第一人称回答：**

我先判断所谓“跑飞”是进入异常、卡在循环、任务不再调度，还是反复复位。先保留现场，再决定排查方向；没有进入 HardFault 的卡死，不能仅靠故障寄存器解释。

以具备这些寄存器的 Cortex-M3/M4 为例，进入 HardFault 后，我会保存异常返回信息，识别使用 MSP 还是 PSP，在栈帧有效的前提下提取 PC、LR、xPSR 和通用寄存器，再结合下面三个寄存器：

1. **HFSR：看为什么到了 HardFault。** `FORCED` 表明某个可配置故障升级成了 HardFault，下一步应看 CFSR；`VECTTBL` 则提示异常向量读取发生总线错误。
2. **CFSR：看具体故障类型。** 它包含 MemManage、BusFault 和 UsageFault 状态。例如 `PRECISERR` 提示精确数据总线错误；`INVSTATE`、`UNDEFINSTR` 可引导我检查非法跳转或损坏代码。不同标志对应不同方向，不能看到 HardFault 就认定栈溢出。
3. **BFAR：看出错访问地址。** 只有 CFSR 的 `BFARVALID` 置位时，我才把 BFAR 当作有效故障地址。再比较地址是否落在合法 RAM、外设或 Flash 区域，检查空指针、越界和错误地址计算。若是 MemManage 地址故障，则按 `MMARVALID` 判断 MMFAR 是否有效。

例如，`HFSR.FORCED=1` 且 `CFSR.PRECISERR=1`，我会结合有效 BFAR 与堆栈 PC，对照本次构建的 ELF 和反汇编找到出错访存指令；若是 `IMPRECISERR`，当前 PC 未必就是最早出错的写指令，要结合前序操作和跟踪信息继续缩小范围。

如果是反复复位，我会先保存复位原因和上次故障记录；如果只是卡死，就暂停 CPU 查看 PC、调用栈、锁和调度状态。读取现场时还要考虑压栈失败、浮点扩展帧和内核差异，避免诊断代码再次触发异常。

技术核对：[ST Cortex-M4 编程手册 PM0214](https://www.st.com/resource/en/programming_manual/DM00046982-.pdf)。

## 6. 程序跑飞可能由哪些原因导致？

**第一人称回答：**

我会从内存、控制流、并发时序和硬件四类检查，不会直接认定是某一种原因。

1. **内存被破坏：** 数组或 memcpy 越界、野指针、释放后使用、任务栈不够、DMA 写错地址，都可能破坏返回地址或关键对象。
2. **控制流非法：** 函数指针损坏、错误的中断向量或 Bootloader 跳转、无效异常返回，都可能让 CPU 跳到不该执行的位置。
3. **并发与状态错误：** 中断、任务和 DMA 缓冲所有权不清，复合操作竞争，错误使用 RTOS API，或者死锁、无超时等待，也可能表现为“跑着不动了”。未定义行为可能在 Release 优化后才暴露。
4. **硬件或运行条件：** 供电波动、时钟异常、外设错误、看门狗复位等，需要结合复位标志和波形判断，不能全部当作软件指针问题。

我会用故障类型、地址、PC、栈水位、错误计数和最近操作来排除假设。找到越界或竞争后，再用边界检查、所有权约束、硬件观察点和原工况回归验证修复。

## 7. Modbus RTU 每帧前突然多出 00，怎样排查和处理？

**第一人称回答：**

我先确认“00”指一个 `0x00`、两个零字节，还是打印出来的字符，并区分它真实出现在总线上，还是只出现在软件缓冲区。我的第一步不会是直接删除帧头零字节。

1. **同时观察线上数据和软件记录。** 用逻辑分析仪看发送端 TX、接收端 RX，以及 RS485 的 DE/RE。若线路上没有多余字节，而日志有，就检查接收长度、DMA 剩余计数、环形索引、首字节写入位置和上一帧残留。零初始化缓冲不能代替有效长度。
2. **若线上也有 00，继续定位来源。** 发送端 TX 已多出零时，检查发送缓冲起始地址和长度；TX 正常但接收端出现异常时，检查空闲电平、收发器使能切换、偏置与故障保护、接地及干扰，并查看 UART 的 FE、NE、ORE 等状态。线路持续低电平可能被识别为零数据并伴随帧错误，但要以波形为证据。
3. **核对串口与判帧。** 检查两端波特率、字长、校验和停止位；按 RTU 静默间隔重新同步，再校验地址、功能码、长度与 CRC。UART IDLE 事件本身不等于已经满足完整 RTU 帧间隔。
4. **按根因修复并回归。** 缓冲错误修正长度和索引；方向切换错误修正使能时序；硬件异常处理空闲电平与信号完整性。再连续轮询，比较异常字节、CRC 错误和超时计数。

我不会无条件过滤 `0x00`，因为它可以是合法数据，也可能是广播地址。丢弃已判定无效的接收候选帧后，应在合法帧边界恢复解析，而不是靠删字节把错误隐藏起来。

技术核对：[Modbus 串行规范中的 RTU 判帧规则](https://www.modbus.org/file/secure/modbusoverseriallegacy.pdf)。

## 8. SPI 接收正常，但发送不对，怎样排查？

**第一人称回答：**

我先明确 MCU 是主机还是从机，以及“发送不对”是 MOSI 波形错误、对方收到的数据错误，还是 Flash 没有按预期写入。这三种现象的定位方向不同。以 GD32 主机连接外部 Flash 为例，我会按下面顺序检查。

1. **检查发送数据源。** 确认缓冲内容、长度、指针和 8/16 位数据宽度是否匹配。使用 DMA 时检查请求映射、方向、地址递增、传输计数和数据对齐，确认完成前缓冲没有被复用；带 Cache 的平台再检查 DMA 可见性。
2. **比较总线波形。** 同时抓 CS、SCK、MOSI 和 MISO，核对 CPOL/CPHA、位序、时钟个数、片选建立与保持时间，以及最后一位发完前是否提前释放片选。发送寄存器空或 DMA 完成，不一定代表线上事务已经结束，具体完成标志要看该芯片 SPI 实现。
3. **隔离软件路径。** 用短的固定数据，在较低时钟下做轮询对照，再恢复中断或 DMA。若只有 DMA 路径失败，重点检查缓冲生命周期和配置；若所有路径都错，继续查引脚复用、电气连接和器件要求。同时按外设手册处理接收数据与错误标志，避免全双工发送期间的接收溢出影响后续事务。
4. **区分“发送正确”和“器件执行成功”。** 若 MOSI、时序都正确，但 Flash 内容不变，我会检查命令、地址、写使能、保护状态、擦除、页边界、忙状态和回读结果。读 JEDEC ID 成功，只说明某一条读事务成功，不代表编程流程也正确。

如果 MCU 实际是 SPI 从机，我还会检查主机提供的时钟与片选，以及首个时钟到来前发送数据是否已经准备好。

技术核对：[ST SPI 通信指南 AN5543](https://www.st.com/resource/en/application_note/an5543-enhanced-methods-to-handle-spi-communication-on-stm32-devices-stmicroelectronics.pdf)。具体寄存器语义仍以项目 MCU 手册为准。

## 9. 串口 IAP 用的是什么协议？

**第一人称回答：**

我会把传输接口和升级协议分开说明。UART 负责传输字节，IAP 是在应用内编程的一类升级方式，两者本身都没有规定唯一的固件文件传输协议。真正的协议要看上位机工具和 Bootloader 接收状态机。

目前我能确认的是项目有独立 Bootloader 和串口 IAP；具体采用 YMODEM、XMODEM 还是自定义分包，需要按工程代码核实，我不会直接把“串口 IAP”当作协议名。

如果代码采用 **YMODEM**，我会说明它承担文件信息与数据分块传输，并通过包编号、校验和确认/重传组织传输；设备端还需要做目标分区、镜像长度、完整性与启动检查。如果是 **自定义协议**，我会结合真实帧格式说明命令、任务标识、偏移、长度、数据、校验和应答，以及超时、重复包与结束确认如何处理。

我也会区分芯片厂商内置的 ROM 下载协议与自己编写的 IAP 协议。厂商 ROM Bootloader 能通过串口下载，不代表我的独立 Bootloader 就用了相同报文。

**核实入口：** 查看上位机发送选项、协议解析函数、包头和应答常量，以及结束与重传流程。确认后，面试开头直接说真实协议名称，再解释帧和恢复机制。

技术核对：ST 的 [USART IAP 示例](https://www.st.com/en/embedded-software/x-cube-iap-usart.html)使用 YMODEM；[AN3155](https://www.st.com/resource/en/application_note/an3155-how-to-use-usart-protocol-in-bootloader-on-stm32-mcus-stmicroelectronics.pdf)描述厂商 Bootloader USART 协议。二者用于区分概念，不用于推断本项目采用哪一种。

## 10. 软重启压力测试中，你怎样定位异常？

**第一人称回答：**

我在大华主要负责软重启压力测试模块，定位时先确定失败发生在哪个阶段，再把测试平台、通信链路和设备端的证据对应起来。

1. **按状态定位。** 一轮分为前置检查、重启命令、确认离线、重新上线、服务就绪和业务校验。设备在线但业务探针失败，应归到业务恢复阶段，不能算整轮成功。
2. **保留关联信息。** 按设备、轮次、请求和时间戳记录最后成功状态、接口响应、错误码、耗时与前后日志，让开发能够还原故障发生前做了什么。
3. **先排除误判。** 检查平台自身和网络是否正常，必要时用在线状态、启动计数和业务接口等独立证据交叉验证。命令超时也可能是设备已重启、应答丢失，不能立刻重复下发重启。
4. **缩小复现条件。** 固定固件版本、设备和负载，逐项调整轮间隔、网络条件等因素，确认异常与什么条件有关；修复后按原条件复测，并加入长时间回归。

我负责的是测试流程、异常识别和现场信息采集；涉及设备内部固件根因时，会把证据交给对应开发并配合复现，不把团队修复全部说成自己独立完成。

## 11. 哪些场景可能导致栈溢出？

**第一人称回答：**

我会重点检查大局部数组、递归或很深的调用链、复杂库函数调用、异常嵌套，以及任务栈本身配置过小。比如格式化输出和浮点格式化，可能比普通业务函数使用更多栈。

在 FreeRTOS 中，我还会区分任务通常使用的 PSP 和异常处理常用的 MSP，结合具体移植查看异常入栈、嵌套和浮点上下文，不能把所有 ISR 用栈都简单算到一个任务里。栈大小配置的单位也要看 API，不能把字节数与 StackType_t 元素数混用。

排查时，我会结合调用链估算、栈填充水位、溢出检测和异常路径压力测试确定余量。同时区分“栈容量不够”与“其他越界写把栈破坏了”，后者单纯增大任务栈解决不了。

具体哪些调用最耗栈，需要看编译结果和测量，不能只因为任务正常运行过一次就判断栈足够。

## 12. volatile 的作用和适用场景有哪些？

**第一人称回答：**

我把 volatile 理解为对编译器访问行为的约束：对象可能被普通代码路径之外的因素改变，编译器应按实现规定保留对它的访问，不能只用先前缓存到寄存器的值代替读取。

常见场景是内存映射的外设寄存器，以及符合平台约定的 ISR 与主流程共享简单标志。例如主流程等待一个由中断更新的标志时，需要避免编译器把读取优化掉；只读硬件状态寄存器还可以使用 const volatile。

但 volatile 不提供互斥，不保证 `count++` 这样的复合操作原子，也不能替代线程同步、内存屏障或 Cache 维护。多个任务共享数据时，我会使用锁、临界区、原子操作或消息传递；DMA 缓冲则另外处理所有权与一致性。

<a id="round2-13"></a>

## 13. sizeof 和 strlen 有什么区别？

**第一人称回答：**

sizeof 是运算符，得到类型或对象所占的字节数；strlen 是字符串函数，计算第一个 ` ` 之前的字节数，不包含终止符。sizeof 通常在编译期确定，但 C 的变长数组等情况可能涉及运行期计算；strlen 的输入必须指向有效的、以零结尾的字符串。

例如 `char a[] = "abc";`，`sizeof(a)` 是 4，`strlen(a)` 是 3。如果写成 `char *p = a;`，`sizeof(p)` 得到的是指针大小，而 `strlen(p)` 仍然是 3。数组作为函数参数时会调整为指针类型，不能在函数里对那个参数用 sizeof 推回原数组容量。

在串口和升级场景中，我不会用 strlen 计算二进制报文长度，因为合法数据里可能包含 `0x00`；应传递明确的有效长度。如果缓冲没有终止符，strlen 还可能越界读取。

技术核对：[GNU C sizeof 说明](https://www.gnu.org/software/c-intro-and-ref/manual/html_node/Type-Size.html)、[GNU C Library 字符串长度说明](https://www.gnu.org/software/libc/manual/2.22/html_node/String-Length.html)。

## 14. 拿到一个新项目，你怎样从 0 到 1 完成？

**第一人称回答：**

我会先把需求变成可验证的指标，再逐步完成最小闭环、异常处理和交付，不会一开始就把所有模块一起写。

1. **明确需求与验收。** 先确认输入输出、使用场景、响应期限、精度、通信对象、功耗成本和故障后的行为。比如液压控制，要把位置误差、调节时间、负载工况与失联处理说清楚；采集终端则要明确数据周期、离线时长和升级恢复要求。
2. **分析约束与风险。** 阅读原理图和芯片手册，核对外设、引脚复用、RAM/Flash、时序及驱动能力。对陌生器件、关键链路和难达成指标，先做验证，避免完整软件写完才发现硬件资源不足。
3. **拆分架构和接口。** 明确驱动、协议、业务、状态管理和测试的边界，定义数据格式、错误码、缓冲所有权、任务与中断分工，列出里程碑和依赖。
4. **先跑通最小闭环。** 从启动、时钟、调试串口做起，逐个验证采集与输出，再接入通信和业务。液压项目可以先验证反馈到阀控的链路，工业终端可以先实现一次采集、上报和命令应答，之后再扩展缓存与升级。
5. **逐步加入可靠性。** 完善参数检查、超时、重试、掉电恢复、看门狗、故障状态和日志，验证并发、边界和长期运行。控制与功率输出还要先明确安全行为，再做联调。
6. **验收和交付。** 按最初指标保存测试条件、版本和结果，整理构建烧录方法、接口与配置文档、已知限制及回归用例，保证其他人能够复现和维护。

如果项目由团队完成，我会明确自己负责的模块，先对齐接口和联调节点；遇到计划风险及时用测量或验证结果反馈，而不是到最后才暴露问题。

## 15. 结构体 struct 和联合体 union 有什么区别，适合什么场景？

**第一人称回答：**

我主要从成员是否同时存在、内存布局和使用方式来区分。

1. **struct 的成员各有自己的存储。** 它适合表示同时有效的一组属性，例如传感器快照里的位移、油温、状态和时间戳。成员之间和结构体尾部可能有对齐填充，所以 sizeof 不一定等于成员大小直接相加。
2. **union 的成员共享存储。** 它适合同一时刻只需要一种表示的场景，例如消息负载可能是温度，也可能是错误码。大小要容纳最大成员并满足对齐要求，不能只记成“永远等于最大成员的裸大小”。
3. **我会配合类型标签使用 union。** 标签说明当前有效成员，写入和读取保持一致，避免上层不知道这块数据现在代表什么。读取另一成员涉及对象表示和语言规则，不能作为通用、安全的类型转换方法，C 与 C++ 的规则也不同。

```c
#include <stdint.h>

typedef enum {
    EVENT_TEMPERATURE,
    EVENT_ERROR
} EventType;

typedef struct {
    EventType type;
    union {
        float temperature;
        uint32_t error_code;
    } data;
} Event;

/* 设置一种消息时，同时设置标签和对应负载。 */
Event make_error(uint32_t code)
{
    Event event = {0};
    event.type = EVENT_ERROR;
    event.data.error_code = code;
    return event;
}
```

这个例子中，外层 struct 让标签和数据同时存在，内层 union 复用不同负载的空间。用于串口或 CAN 通信时，我仍会逐字段编码，不能直接发送整个对象内存，因为还涉及对齐、端序和浮点表示。

技术核对：[GNU C 联合体与对齐说明](https://www.gnu.org/software/c-intro-and-ref/manual/html_node/Unions.html)。
