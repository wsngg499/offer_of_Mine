# 联芸科技一面面经第一人称回答

按《一面面经.docx》原题顺序整理，共 10 题。回答结合液压伺服多控制器项目、GD32 工业采集终端和大华实习，适合先口述主体，再根据追问展开。

事实边界：现有简历明确了 STM32F1 采集节点、STM32F4 核心控制器、STM32F1 执行节点，以及 GD32、W25Q64、EEPROM 和独立 Bootloader；没有明确完整料号、实际节点数量、采样周期、波特率和真实故障记录。下文涉及这些内容时注明依据或示例，不能把示例数字和参考案例当成实测经历。

## 1 简介两个项目。

**第一人称回答：**

我的第一个项目是多控制器协同的液压伺服运动控制系统，目标是实现液压缸的位置闭环和阀组协同控制。我把系统分成采集、核心控制和执行三层：采集节点使用 STM32F1 和 FreeRTOS，完成位移、液位、油温的 ADC 采集、滤波和标定，通过 RS485 上的 Modbus RTU 向核心提供数据；核心 STM32F4 轮询反馈并运行位置 PID，经过限幅和方向处理后，通过 CAN 下发阀控命令；执行节点使用 STM32F1，把命令转换为 PWM 和方向信号，驱动四路阀控通道。我主要负责核心控制与通信软件，并参与节点联调和异常处理。简历中记录的结果是 10 mm 阶跃下定位误差约 ±0.05 mm、调节时间约 0.5 s，测试口径需要以实际记录为准。

第二个项目是基于 4G 云端运维与可靠升级的工业采集终端。GD32 负责温度、压力采集及风机、继电器控制，通过 4G 和 MQTT 接入 OneNet，实现周期上报、命令处理、心跳、掉线重连和离线缓存。我主要负责通信与升级软件，编写独立 Bootloader，使用外部 W25Q64 暂存固件、EEPROM 保存版本和升级状态，实现串口 IAP 和 OTA，并测试下载中断、错包、版本不匹配和升级掉电等恢复场景。

**回答重点：** 每个项目讲清楚“解决什么问题—模块如何连接—自己负责什么—如何验证”，不要只列芯片和协议。

## 2 第一个液压控制项目有多少个采集节点，对应一个核心控制器？

**第一人称回答（按现有三 MCU 架构材料整理，面试前核实实际硬件数量）：**

按这套三 MCU 实验系统的架构，是一个采集节点、一个核心控制器和一个执行节点。采集节点内部有多个 ADC 通道，分别处理位移、液位、油温等传感器，所以“多个采集通道”不等于“多个采集节点”。核心 F4 通过 Modbus RTU 读取这个采集节点的数据，再把控制命令通过 CAN 发给执行节点。执行节点控制四路阀，也不等于有四个执行 MCU。

如果后续扩展多个采集节点，可以让每个 Modbus 从站有独立地址，由核心按调度轮询。但节点增加后，总线占用和等待时间也会增加，需要重新核算轮询周期、超时和反馈数据年龄，不能认为接上更多节点以后实时性不变。

**如果实际有多个采集板：** 第一段必须改成真实数量，随后说明每个从站地址、各自采集的信号，以及哪些反馈进入闭环。现有材料支持的是三层三 MCU 的叙述，不是独立硬件清点结果。

## 3 为什么用 Modbus 和 CAN 两种通信方式？

**第一人称回答：**

我主要根据采集和执行两侧的数据特点来选。采集侧是位移、液位、油温等周期性工程量，用 RS485 加 Modbus RTU 可以把数据和有效状态映射为寄存器，核心按周期读取，接口比较清晰，也方便用现成工具调试。RS485 的差分传输适合工业现场，但寻址、校验和请求响应规则由 Modbus 来实现。

执行侧传的是短小的阀控指令与节点状态，对及时性和异常恢复更敏感，因此采用 CAN。CAN 提供基于 ID 的无破坏仲裁、硬件 CRC、错误检测和故障隔离，可以让不同类型报文有明确优先级。应用层仍要检查命令范围、序号和超时，不能只依赖 CAN 的硬件机制。

如果全部是自研节点，统一成 CAN 也可以评估，优点是协议维护更简单；现在这套方案是按采集与执行的功能划分选择。它的代价是核心需要管理两种协议，所以我还要保证通信过程与 PID 计算解耦，Modbus 等待超时不能拖住控制周期。

**追问要点：** CAN 不天然保证所有报文都及时到达，仍需分析优先级、总线负载和错误重试；也不要把 RS485 和 Modbus 当成同一层协议。

## 4 周期采集与上传，大概多久采一次，多久上传一次？

**第一人称回答：**

我会把三个周期分开说明：第一是 ADC 原始采样周期，第二是滤波、标定后发布数据快照的周期，第三是核心通过 Modbus 读取数据的周期。原始采样可以更快，用于滤波和异常检测；通信读取的频率要根据控制需求与总线带宽确定，不一定每采一个点就传一帧。

在我的架构中，采集节点是 Modbus RTU 从站，“上传”具体是核心发起读取后，从站返回最近一份完整快照，不是从站随意主动发送。位移反馈与闭环直接相关，需要优先保证更新及时；液位和油温变化较慢，可以采用较低处理频率，但要保留各自的新鲜度或更新时间。

具体周期应从定时器、ADC/DMA 配置、任务周期和主站轮询程序中确认。我选择周期时会综合采集处理延迟、Modbus 请求响应时间、控制周期和数据允许的最大年龄，再通过压力测试验证。不能只因为机械调节时间约 0.5 s，就直接推导出唯一的采样频率。

### 被追问数字时，如何解释一组合理配置

以下仅为预算示例，不是已确认的项目配置：

| 环节 | 示例设置 | 作用 |
|---|---|---|
| 完整 ADC 扫描 | 每 1 ms 一批 | 为各通道提供原始数据 |
| 快照更新 | 每 5 ms 一次 | 发布滤波标定后的完整数据 |
| Modbus 主站轮询 | 每 10 ms 一轮 | 获取采集节点最新快照 |
| 核心控制计算 | 每 10 ms 一次 | 使用有效且未过期的反馈计算控制量 |

在这个例子中，核心每秒最多收到约 100 次轮询结果，不能说成每秒有 1000 次新位置反馈。快照与轮询不同步时，还会增加数据年龄；滤波也带来延迟，均需计入闭环分析。

还要检查串口带宽。例如仅假设读 3 个 16 位寄存器，请求 8 字节、正常响应 11 字节，在 115200 bit/s、每字符 11 bit 的配置下，纯线上数据时间约为 `19 × 11 / 115200 ≈ 1.81 ms`。这还不包含 RTU 帧间静默、收发切换、从站处理和调度时间，所以不能拿 1.81 ms 当完整事务耗时。在 9600 bit/s 下，相同纯数据时间约 21.8 ms，显然无法满足 10 ms 完整轮询周期。

**面试前必须补齐：** 原始采样周期、发布周期、轮询周期、控制周期、串口帧格式和波特率，以及一次读多少寄存器。没有记录时不要背示例为实际参数。

## 5 Modbus RTU 传输中会不会丢包？丢包怎么处理？

**第一人称回答：**

会出现请求丢失、响应缺失或帧损坏。严格说在串行链路上，可能是干扰导致字节错误、串口溢出、接收缓冲覆盖、RS485 收发方向切换不及时，或者从站忙导致响应超时。Modbus RTU 的 CRC 用于检测帧错误，但不自动保证这次业务一定完成，超时和重试需要主站软件设计。

主站发出请求后启动响应期限，接收时检查地址、功能码、预期长度与 CRC。错误帧不进入反馈数据；到期没有有效响应，就记录错误并执行有限重试。收到 Modbus 异常响应时，还要区分非法地址等确定性配置错误与临时忙状态，不能所有错误都无限重发。

对闭环而言，我会将通信与控制解耦：控制程序读取最近一份完整有效快照，同时检查数据年龄。短时丢帧是否允许继续用旧值，要由控制和安全要求决定；超过允许期限后退出正常闭环并进入既定故障处理。执行节点还需要本地 CAN 命令超时保护，避免核心或通信异常后一直保持旧动作。

### 进一步追问时可以补充

- **重复读取是否有副作用：** 普通读寄存器通常可以重试；对写动作，尤其启动、计数或清除等特殊语义，需要先明确重复执行的后果。
- **迟到响应怎样处理：** Modbus RTU 没有 Modbus TCP 那样的事务标识，通常一次只保留一个未完成请求；结合预期响应格式、接收状态和超时恢复处理迟到帧。相同请求的迟到响应与新响应可能无法仅凭报文区分，必要时在应用寄存器中增加采样序号或时间信息。
- **CRC 正确是否代表新数据：** 不代表。CRC 只检查传输内容，数据是否过期需要单独判断。

## 6 Bootloader 是怎么起来的？

**第一人称回答：**

我会把芯片硬件启动和自己编写的 Bootloader 分开讲。以项目所用 Cortex-M 型 GD32、配置从内部主 Flash 启动为前提，复位时处理器从启动映射对应的向量表读取初始栈指针和复位入口。因为我把独立 Bootloader 链接并烧录在这个启动区域，所以先进入的是 Bootloader 的 Reset_Handler，而不是 Application 的 main。

启动代码完成 C 运行环境建立，包括初始化数据段、清零 BSS，并按具体工具链启动流程执行 SystemInit 等初始化，然后进入 Bootloader 的 main。接着它初始化必要的时钟、存储接口和状态读取功能，检查 EEPROM 中的升级状态，以及内部应用或外部镜像的有效性。

如果应用有效且没有待安装任务，就进入应用；如果存在已校验的候选镜像，就执行安装；如果应用不可用，则进入恢复或等待升级的路径。因此 Bootloader 本质上是一份有自己启动文件、链接布局和 main 的独立程序，只是被安排在复位后优先执行的位置。

### 如果追问如何跳转 Application

**第一人称补充：**

我先验证应用镜像和向量表：初始 MSP 是否在芯片允许的 RAM 范围、满足对齐要求，复位入口是否为合法的 Thumb 地址并落在应用范围。然后停止 Bootloader 使用的 SysTick、DMA 和外设中断，处理待处理中断，设置应用的向量表基址，并按启动约定恢复处理器状态，加载应用 MSP 后跳转到应用 Reset_Handler，让应用自己的启动代码完成初始化。

修改 MSP 后不能再随意使用原 Bootloader 的 C 栈，所以最后的跳转要用经过验证的底层实现；全局中断屏蔽状态也要与应用启动流程约定一致。不能只把应用起始地址强转成函数指针直接调用。

**追问要点：** 具体启动映射、VTOR 支持情况、RAM 范围和外设复位行为必须按 GD32 完整型号确认；厂商内置 ROM Bootloader 与自己写在 Flash 中的 Bootloader 是两回事。

## 7 编写独立 Bootloader 实现的是哪一部分功能？

**第一人称回答：**

我主要用它实现升级安装和启动管理。应用程序负责正常采集、控制和 4G/MQTT 通信，把固件下载到外部 W25Q64；Bootloader 根据升级状态验证镜像，擦写内部 Application 区并回读检查，再决定是否启动应用。串口 IAP 的接收和升级入口也可以由 Bootloader 提供，具体按工程分工实现。

它与应用独立，是因为覆盖内部应用时，应用自身不能被当作可靠的恢复入口。如果下载或安装中断，Bootloader 仍应能启动、识别不完整状态，并从有效外部镜像重新安装或进入恢复模式。

我的边界是 Bootloader 保持精简，负责镜像检查、安装、状态和跳转，不把 PID、传感器业务等都放进去。若实现了旧镜像备份和试启动确认，还可以扩展回滚；如果没有这些机制，就不能仅凭“有 Bootloader”保证旧版本可恢复。

| 模块 | 主要职责 |
|---|---|
| Application | 正常业务、联网、下载与暂存固件 |
| Bootloader | 校验镜像、安装应用、检查状态、启动或恢复 |
| W25Q64 | 保存完整候选镜像，若实现则同时保留旧镜像 |
| EEPROM | 保存版本、升级阶段及可验证的恢复信息 |

**追问要点：** 固件可启动不代表业务正常；健康确认、备份和回滚是额外设计，需核实实际实现。

## 8 有一个 32 比特的数据，将某一比特写成 0，代码怎么写？两种方法。

**第一人称回答：**

我先约定位编号从最低位 0 开始，到最高位 31，并使用 uint32_t 保存数据，避免有符号位移问题。最常用的方法是生成目标位掩码，取反后按位与：目标位与 0 得到 0，其他位与 1 保持不变。

第二种方法是先提取目标位，再与原数异或。原来目标位为 1，就异或 1 清零；原来为 0，就异或 0 保持，因此也能实现无条件清零。不能直接写 x 异或掩码，那样会把原来的 0 翻成 1。

```c
#include <stdint.h>

/* 方法一：取反掩码后按位与，通常优先使用。 */
uint32_t clear_bit_and(uint32_t x, unsigned int bit)
{
    if (bit >= 32u) {
        return x;  /* 示例约定：非法位号保持原值；业务接口也可返回错误。 */
    }
    uint32_t mask = (uint32_t)1u << bit;
    return x & ~mask;
}

/* 方法二：提取目标位，再异或清除。 */
uint32_t clear_bit_xor(uint32_t x, unsigned int bit)
{
    if (bit >= 32u) {
        return x;
    }
    uint32_t mask = (uint32_t)1u << bit;
    return x ^ (x & mask);
}
```

例如 `x = 0x000000AC`，二进制低 8 位为 `10101100`，将第 3 位清零后，两种方法都得到 `10100100`，即 `0x000000A4`。

### 嵌入式场景的加分补充

**第一人称补充：**

如果操作的是硬件寄存器，我还会先看寄存器写入语义。普通可读写寄存器可能支持这种读改写，但 W1C，也就是写 1 清零的状态位，需要按手册向对应位写 1，不能套用普通变量清位公式。寄存器还可能被中断或其他上下文同时修改，读改写不自动具有原子性；volatile 也不提供互斥，应优先使用芯片提供的置位/清位寄存器，或者采取合适的同步方法。

**避免混淆：** `x & (x - 1)` 清的是最低一个为 1 的位，不能用来指定任意位号。

## 10 举一个项目中遇到的比较大的问题，讲讲怎么解决。

**案例选择：** 优先准备与真实记录一致的液压项目通信问题，因为它能体现从协议现象定位到外设时序的能力。下面沿用已有问答中的 TXE/TC 参考案例，但现有材料没有原始波形或代码证明其实际发生；确认后再作为个人经历使用。

**第一人称口述模板：**

液压项目联调时，一个比较棘手的问题是 Modbus 响应偶尔长度不完整或者 CRC 失败。因为大部分时候都正常，单看应用层只能看到通信异常，无法马上判断是数据内容错了，还是发送接收过程有问题。

我先在主从两侧记录接收字节数、CRC 错误和超时次数，对比正常帧与异常帧，发现问题主要集中在响应尾部。然后用逻辑分析仪同时观察 UART TX 和 RS485 的发送使能 DE，检查最后一个字节结束与方向切换的关系。

定位后发现，发送逻辑把 TXE 当成整帧完成条件。TXE 只说明发送数据寄存器空了，最后一个字节可能仍在移位寄存器中发送；这时提前关闭 DE，就会截断尾字节。修改后我等待 TC，也就是最后一个停止位发完，再切回接收。

验证时先确认波形上方向切换发生在帧结束之后，再做连续轮询和不同负载下的回归，比较原来的尾部截断是否消失，以及错误和超时统计是否改善。这次定位的关键是用接收统计缩小范围，再用硬件波形验证，而不是看到 CRC 错就先修改 CRC 算法。

### 如果继续追问

**为什么是偶发？**

我会检查原程序从检测 TXE 到关闭 DE 之间的实际执行路径和延迟是否变化，以及 UART/DMA 的具体用法。错误时机可能受中断、调度或软件路径影响，但这个解释需要波形支持。如果每次都以相同方式提前关闭，现象也可能是稳定失败，不能只用“时序问题”解释所有偶发性。

**用了 DMA 以后，还需要等 TC 吗？**

需要区分 DMA 传输完成和 UART 线路发送完成。DMA 完成可能仅表示最后一份数据已经送到串口外设，移位寄存器仍在发送；RS485 切回接收应以 UART 真正发送完成的条件为依据，并遵循驱动库的完成回调语义。

**为什么 CRC 校验失败不一定是 CRC 算法问题？**

因为字节缺失、长度处理错误、数据被覆盖都可能让最终 CRC 对不上。我要先确认参与计算的原始数据是否完整，再检查算法和参数。

**没有这个真实案例怎么办？**

使用自己实际遇到的 OTA、RTOS 或大华测试问题，保持同样的表达结构：现象、影响、证据、根因、个人修改、复测结果。不要把参考案例的完整程度当作经历真实性。
